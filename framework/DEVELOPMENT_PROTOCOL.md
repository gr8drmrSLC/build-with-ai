# DEVELOPMENT_PROTOCOL.md

The 8-step regression safety protocol for every change to working
code. This protocol exists because AI agents are fast and confident —
two properties that combine badly without a safety structure.

The most common AI-assisted development failure mode is not a bad
suggestion. It is a good suggestion that works in isolation and
silently breaks something adjacent. This protocol prevents that.

---

## The Protocol

Every change to existing, working code or files follows these steps
in order. Steps are not optional. Steps are not batched.

### Step 1 — State what is currently working and must not break

Before touching anything, write down (in the task, in a comment,
or out loud) exactly what the current working state is.

**Why**: this forces you to define "done" for the regression check
at Step 6. If you cannot state what is currently working, you
cannot verify that it still works after your change.

**Example**:
> "The API client successfully calls `/v1/messages` and returns
> a parsed response. The budget guard correctly blocks calls
> over the session limit. Both are covered by smoke_test.py."

### Step 2 — Identify the smallest change that achieves the goal

Before writing any code, identify the minimum surface area of
change. Resist the pull to clean up adjacent code, fix unrelated
issues, or "improve" things you notice while you're in there.

**Why**: every additional line changed is an additional line that
could introduce a regression. Scope creep in a single change is
the most common source of hard-to-diagnose bugs.

**Example**:
> "The goal is to add retry logic to the API client. The smallest
> change is a retry wrapper around the single `_call()` method —
> not a refactor of the entire client."

### Step 3 — Check whether the change affects any other file or system

Search for every place the code you are changing is called, imported,
or depended upon. If the change is to a function signature, find
every caller. If it is to a config key, find every reader.

**Why**: a change that is locally correct can be globally breaking.
This step makes the blast radius visible before the change is made.

**Tools**:
```bash
# Find all imports of a module
grep -r "from core.api_client" src/ tests/

# Find all calls to a function
grep -r "def call_api\|call_api(" src/ tests/

# Find all references to a config key
grep -r "ANTHROPIC_API_KEY" src/ .env.example
```

### Step 4 — Make the change

Now make the change. The smallest change identified in Step 2,
informed by the blast radius identified in Step 3.

If you discover during the change that the scope is larger than
identified in Step 2, stop. Reassess. Do not expand scope
mid-change — complete the small change, verify it, commit it,
then start a new task for the additional work.

### Step 5 — Verify the change works

Run the appropriate verification for the type of change:

| Change type              | Verification                                  |
|--------------------------|-----------------------------------------------|
| Python code              | `python -m pytest tests/` or `python smoke_test.py` |
| TypeScript/React         | `npm run build` (tsc + vite)                  |
| Config or environment    | Start the application and check the relevant path |
| Documentation only       | Read it. Check links. Verify accuracy.        |
| Infrastructure/workflow  | Validate syntax; check dry-run if available   |

If there are no tests, the minimum verification is running the
code path that was changed and confirming it behaves as expected.
"It looks right" is not verification.

### Step 6 — Verify nothing that was working before is now broken

Return to the working state defined in Step 1. Verify each item
in that list still works.

**Why**: a change can pass its own verification (Step 5) and still
break something else. This step is the regression check. It is
distinct from Step 5 and cannot be skipped.

**Example**:
> Step 1 stated: "API client calls work, budget guard blocks overages,
> both covered by smoke_test."
> Step 6: run smoke_test.py. All tests pass. Proceed.

If anything that was working in Step 1 is now broken, stop.
Fix the regression before committing anything.

### Step 7 — Commit with a message that explains why, not just what

See `GIT_POLICY.md` for commit message format. The key rule:
the diff shows what changed. The commit message explains why
the change was necessary.

A commit message that could have been generated by reading the
diff is not a useful commit message.

**Example**:
```
Add exponential backoff to API client

Without this, a transient 529 from Anthropic would fail the
entire task with no retry. Backoff caps at 32s with 3 attempts
before raising — enough to survive rate-limit windows without
blocking indefinitely.
```

### Step 8 — Update PROJECT_STATUS.md and DECISIONS.md

If the change was significant — a new capability, a resolved open
question, a non-obvious architectural choice — update:

- `PROJECT_STATUS.md`: reflect new working state; update "next task"
- `DECISIONS.md`: add an ADR if the change involved a decision that
  should be remembered and not relitigated

Not every change requires an update. A bug fix with an obvious
cause does not need an ADR. A choice between two reasonable
approaches does.

## When to Apply This Protocol

**Always apply** when:
- Changing code that is currently working in production or passing tests
- Modifying a file that other files depend on
- Changing a config key, environment variable name, or API contract
- Updating a dependency version

**Apply abbreviated** (Steps 1, 4, 5, 7) when:
- Adding a new file that nothing depends on yet
- Writing a new test
- Documentation-only changes

**Do not skip entirely.** The question is not whether to apply the
protocol — it is which steps are appropriate for the change size.

---

## The Scope Creep Rule

The most common protocol violation is not skipping a step. It is
expanding scope during Step 4 and not resetting.

The pattern: you open a file to make a small change, notice something
adjacent that looks wrong or could be improved, fix it in the same
edit, and now you have two logical changes in one commit, one of
which was not in the blast radius analysis.

The rule: **notice it, log it, finish the current change first.**

```
# Acceptable mid-change behavior
# You notice a related issue while making your change:
# → Note it in PROJECT_STATUS.md as a follow-up task
# → Complete the current change
# → Run the full protocol on the new task separately
```

Discipline here is not pedantry — it is the difference between
a regression that takes 10 minutes to find and one that takes
two days.

## Smoke Test

`tests/smoke_test.py` is the Step 1 baseline for every project.
It verifies the minimum working state: environment loads, core
modules import, key integrations respond. It runs in under 30 seconds.

If `smoke_test.py` fails, the environment is broken and no other
work should proceed until it passes.

```bash
python tests/smoke_test.py
```

A project without a smoke test has no defined baseline. The first
task in any new project using this framework is to write one.
